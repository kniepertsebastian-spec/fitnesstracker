Konzept/Umgesetzt/Verifiziert-Aufbau mehr. Die ausführliche Historie bis hierhin steht in

fortgeführt.

- **Progress Photo Security Review (P0.5)** — Der Upload vertraute bisher komplett dem client-gesendeten Mimetype; eine als "image/jpeg" deklarierte Datei wurde ungeprüft so gespeichert und mit genau diesem (potenziell falschen) Content-Type wieder ausgeliefert, ohne echte Bildvalidierung, Dimensionslimit oder EXIF-Entfernung. Jeder Upload läuft jetzt durch `sharp`: Bytes müssen tatsächlich als JPEG/PNG/WebP dekodierbar sein (sonst 400), Abmessungen über 8000px werden abgelehnt, und die gespeicherte Datei ist eine Neukodierung ohne Metadaten (EXIF/GPS/ICC) statt des rohen Uploads — die tatsächlich erkannte Bildart bestimmt den gespeicherten Mimetype, nicht mehr der Client-Header. Zusätzlich `X-Content-Type-Options: nosniff` auf der Ausliefer-Route. Zugriffskontrolle (Auth + Owner-Check vor Bildzugriff), nicht erratbare Dateinamen (UUID) und echtes Löschen (DB-Row + `unlink` der Datei) waren bereits vorhanden. Verifiziert: API-Checks — echtes Foto mit eingebettetem EXIF hochgeladen, heruntergeladene Datei hat kein EXIF mehr; als "image/jpeg" deklarierte Textdatei mit 400 abgelehnt; 9000×9000px-Bild mit 400 abgelehnt; unauthentifizierter Dateizugriff mit 401 abgelehnt; Datei nach Löschen tatsächlich vom Datenträger entfernt. Typecheck/Build grün.
- **Offline-Sync UX (P0.3)** — Der Header zeigte bisher nur unauffällige Badges bei "Offline"/"X ausstehend"/"X fehlgeschlagen" (letzteres nur mit Hover-Tooltip, auf Mobile unbrauchbar), aber nie einen aktiven "wird gerade synchronisiert"-Zustand, keine Details zu fehlgeschlagenen Änderungen und keine Möglichkeit, es erneut zu versuchen — fehlgeschlagene Mutationen wurden dauerhaft verworfen. Neue `SyncStatusIndicator`-Pille (immer sichtbar, auch im "Alles synchronisiert"-Zustand — vorher gab es dafür kein eigenes Signal) öffnet ein Panel mit Klartext-Status und, bei Fehlern, jedem betroffenen Eintrag einzeln (Übung/Aktion + Fehlermeldung) samt "Erneut versuchen" pro Eintrag und "Alle erneut versuchen". Dafür trägt `FailedMutation` jetzt das ursprüngliche Payload + ein lesbares Label, damit ein Retry die Aktion nicht neu abfragen muss, und ein Ref-Counter (`beginSync`/`endSync`) macht "Synchronisierung läuft" sichtbar, auch wenn beide Warteschlangen (Sätze, Trainingseinheiten) gleichzeitig laufen. Verifiziert: Playwright — Offline gehen + Satz loggen zeigt "Offline · 3 ausstehend" und legt die Änderungen lokal ab; wieder online synchronisiert automatisch auf "Synchronisiert", Server-State bestätigt alle 3 Sätze; erzwungener Server-Fehler (gemockte 400-Antwort) zeigt "3 fehlgeschlagen" mit den einzelnen Gründen im Panel, "Alle erneut versuchen" synchronisiert danach erfolgreich (Server-State erneut bestätigt), kein Overflow bei 390px.
- **Kritische Offline E2E Tests (P0.4)** — Erste committete Playwright-Suite des Projekts (`frontend/e2e/`, `pnpm test:e2e`), da bisher nur Ad-hoc-Skripte für manuelle Verifikation existierten. Läuft bewusst gegen einen echten Produktions-Build (`vite preview`, per `playwright.config.ts` automatisch gebaut/gestartet), nicht gegen `pnpm dev` — ein Reload während "offline" funktioniert nur, wenn ein echter Service Worker die App-Shell aus dem Cache bedient, und den gibt es im Dev-Modus nicht. Jedes Test-File registriert einen eigenen Wegwerf-Account (nie den manuell genutzten `test@example.com`) und deckt den kompletten Flow ab: Login → offline gehen → Satz erstellen/bearbeiten → App neu laden → lokale Daten prüfen → online gehen → Sync → Server-State, plus die vier zusätzlichen Szenarien aus dem Roadmap (mehrere Offline-Änderungen inkl. Mutation Coalescing, Create+Delete offline ohne Server-Kontakt, Sync-Fehler mit Retry).
  - Dabei einen echten Bug gefunden und behoben: Der Zugriffstoken lebt bewusst nur im Speicher (nie in localStorage, gegen XSS) und wird nach jedem Reload per stillem `/auth/refresh`-Aufruf über das httpOnly-Cookie neu geholt — schlug dieser Aufruf fehl, wurde der Nutzer *immer* ausgeloggt, auch wenn der Grund nur ein Netzwerkfehler (offline) statt eines echten 401 war. Ein Reload im Offline-Zustand warf den Nutzer damit auf den Login-Bildschirm, obwohl alle Daten sicher lokal lagen — das Gegenteil von dem, was P0.3 gerade erst zeigen sollte. Jetzt unterscheidet `useAuthBootstrap`, ob der Server tatsächlich "nein" gesagt hat (`ApiError` → echter Logout) oder der Request gar nicht erst ankam (Netzwerkfehler → Fallback auf einen zuletzt bekannten, nicht-sensiblen User-Snapshot in localStorage, kein Token darin). Eine echte Session-Ungültigkeit fängt sich weiterhin über den bestehenden 401-Retry beim nächsten echten Request.
  - Verifiziert: Alle 4 Szenarien zweimal hintereinander grün (keine Flakiness), Typecheck/Build für alle Packages grün, normaler Online-Login/Reload/Logout im Dev-Modus per Playwright gegengecheckt (durch die Auth-Änderung nicht beeinträchtigt).

- **Incident: Backend crash-loop nach dem Deploy von P0.5 (`sharp`)** — Direkt nach `git pull && docker compose up -d --build` auf dem Mini-PC startete der Backend-Container nicht mehr (`exited with code 132` = SIGILL, immer ~30s nach dem Start, nie "Backend listening" erreicht). `sharp`s mitgelieferte `libvips`-Binary nutzt vektorisierte (SIMD/AVX2-)Codepfade, die die schwächere Mini-PC-CPU nicht unterstützt — ein Prozessor-Fault, kein abfangbarer JS-Fehler, der den ganzen Container sofort tötet. Zwei Änderungen: `VIPS_NOVECTOR: "1"` in `docker-compose.prod.yml` zwingt `libvips` auf den universell kompatiblen, nicht-vektorisierten Pfad; `sharp` wird in `progressPhoto.service.ts` jetzt erst beim ersten tatsächlichen Foto-Upload dynamisch importiert statt beim Boot statisch geladen — selbst falls das Problem auf einer Maschine doch fortbesteht, bleibt der Ausfall dann auf den einzelnen Upload-Request begrenzt (sauberer 503) statt die komplette App down zu nehmen. Verifiziert: lokaler Typecheck/Lint/Build grün, echter Foto-Upload gegen den geänderten Code funktioniert weiterhin (Datei landet korrekt, EXIF entfernt, danach sauber gelöscht) — der eigentliche Auslöser (CPU-Instruktionssatz des Mini-PCs) lässt sich in dieser Sandbox nicht reproduzieren, daher Bestätigung des Fixes selbst nach dem nächsten Deploy auf der echten Maschine noch ausstehend.
